# Demo 8 BMS — Verification Failure Diagnosis (2026-07-03)

All 5 specialists failed the acceptance gate in `report.md` (0/5 PASS). This
diagnoses root cause before any further spec rewrites or retrains.

## Root cause 1 (primary): generic non-code prompt template in `crasis/factory.py`

`crasis` is a separately installed package (`/mnt/c/Workspace/crasis`, its own
git repo, not vendored in `smelt`). `arch-build` shells out to `crasis build`,
which runs `generate` (factory.py) -> `train` -> `export` with **no
filtering/validation stage between them**.

Synthetic training data is generated by DeepSeek (`deepseek/deepseek-chat-v3.1`,
factory.py:47) via `_BinaryPromptBuilder.build` (factory.py:291-337). The spec's
`description`/`task.trigger`/`task.ignore` text is spliced in verbatim, but the
surrounding scaffold is generic chat/support-ticket boilerplate: it asks for
"labeled **text examples**" for a "binary **text classifier**", instructs the
generator to "vary tone: formal, casual, frustrated, polite", and calls each
example a "standalone **message or text snippet**" (factory.py:308-327).
Nothing in the scaffold says "C++" or "source code" — only whatever the spec's
own description happens to mention.

**Effect:** negative (clean) training examples skew toward prose-flavored,
off-domain text rather than the real universe of clean C++ shapes (bare
constructors, getters, HAL setters). The model never reliably learns that
ordinary BMS boilerplate is negative. This is spec-independent — it explains
why the false-positive pattern is close to universal across all 5 specialists
(constructors, `is_ready`, `read_temp_raw`, `to_millivolts`, `poll_all`, etc.
all false-positive on 2+ specialists) rather than tied to one rule's wording.

This is the same defect documented for Demo 7
(`feedback_crasis_cpp_specialists.md`), now confirmed to live in shared
infrastructure rather than in any one spec. Rewriting spec text alone (the T4a
BMS-vocabulary retrain) cannot fix it, because the generic scaffold around
that text is what steers the generator off-domain.

Not the cause: class balance. `_BinaryPromptBuilder` requests an exact 50/50
positive/negative split (factory.py:293-295) — confirmed even.

## Root cause 2 (secondary): 128-token truncation vs 512-token chunks

Train/export/eval all tokenize with `max_length=128`
(`train.py:278`, `export.py:256`, `eval.py:162`) using BERT-Tiny
(`google/bert_uncased_L-2_H-128_A-2`, the model resolved for
`max_model_size_mb: 20`). The production chunker allows function-body chunks
up to `_MAX_TOKENS = 512` (`smelt/scorers/chunker.py`). Longer real BMS
functions get silently truncated at both train and inference time, sometimes
cutting off the branch or `return` statement that determines the label.

Measured impact: 12/128 (9%) of verification case files exceed 128 tokens.
Real, but secondary — most of the false positives observed (e.g.
`neg__is_ready.cpp` at well under 128 tokens) are not truncation artifacts.

## Two additional spec-level issues (layered on top, not the main story)

- **`fault-cleared-outside-reset`**: trigger vocabulary lists `false` and `0`
  as generic "cleared values" alongside `FaultType::NONE`. `false`/`0` are
  extremely common tokens in unrelated clean code (any bool return, any
  zero-init), which likely amplifies the FP rate for this specialist beyond
  the baseline root-cause-1 effect. Also confirmed the model dropped the
  "clearing value specifically" qualifier: `neg__shape2_update_cell_sets_only.cpp`
  assigns only fault-*setting* values (`OVER_VOLTAGE`/`UNDER_VOLTAGE`/`OVER_TEMP`,
  never `NONE`) to a `faults_[...]` member and still scores 0.93 positive —
  the model appears to trigger on "assignment to a fault-like member" without
  checking whether the assigned value is a clearing value.
- **`platform-dependent-integer-types`**: `quality.eval_on` itself is skewed
  ~27% positive / 73% negative (6 violation examples out of 22). If synthetic
  generation follows a similar shape despite the 50/50 request, or if the
  6 hand-authored violation examples are too narrow a distribution, it would
  explain the observed 0/6 violation recall (100% specificity, 0% sensitivity,
  violations scored ~0.04 — confidently wrong, not borderline).

## Recommended fix order

1. Patch `crasis/factory.py`'s `_BinaryPromptBuilder` prompt scaffold to
   request idiomatic source code (not "text message"/"tone") whenever the
   spec's language can be detected (e.g. `spec.description` mentions "C++
   function body"). This is a cross-repo change to `/mnt/c/Workspace/crasis`
   (separate git repo, currently clean on `main`) — needs explicit sign-off
   before editing.
2. Raise `max_length` in `train.py`/`export.py`/`eval.py` to 512 to match the
   chunker, or confirm BERT-Tiny's position embedding limit supports it.
3. Retrain all 5 specialists against the fixed pipeline.
4. Only then revisit the two spec-level issues above if they still reproduce.

Fixing spec wording alone (skipping step 1) will not resolve the universal FP
pattern — it would repeat the T4a mistake of treating an infrastructure defect
as a per-spec problem.

---

**Status update (2026-07-05).** Step 1 (prompt scaffold) was fixed as crasis
1.3.1 on 2026-07-03 and all specialists retrained against it. Step 2 (the
128-token truncation) was NOT applied at that time — and it turned out to be
the root cause of the `shape7` reinit-before-evaluate false negative that
survived every subsequent retrain: `shape7`'s redacted chunk is 193 tokens and
its `reset_faults()` call sits past token 128, so the model never saw the
violation at training or inference. There was also a fourth truncation site
this diagnosis missed: `deploy.py` (`Specialist.classify`) truncated at 128 at
runtime, affecting every deployed specialist, not just training. Fixed as
crasis 1.4.0 (`CRASIS_MAX_SEQUENCE_LENGTH`, default 512, all four sites).
Re-verification at 512 showed no regressions on the four passing specialists.
