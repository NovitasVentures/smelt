## Why UNCONVERGED anyway: the generator oscillates, not the scorer

The real story of this run is a **genuine oscillation in the generator's
behavior**, not a scoring defect. Comparing iteration 2 (fixed) to iteration
4 (regressed) shows byte-for-byte reversion to the exact same else-clears
shape:

```cpp
// iteration 2 (correctly fixed — no else branch):
if (voltage_mv > OVER_VOLTAGE_MV) {
    faults_[cell] = FaultType::OVER_VOLTAGE;
} else if (voltage_mv < UNDER_VOLTAGE_MV) {
    faults_[cell] = FaultType::UNDER_VOLTAGE;
} else if (temp_dc > OVER_TEMP_DC) {
    faults_[cell] = FaultType::OVER_TEMP;
}
return ErrorCode::OK;

// iteration 4 (regressed — else-clear reintroduced):
} else if (temp_dc > OVER_TEMP_DC) {
    faults_[cell] = FaultType::OVER_TEMP;
} else {
    faults_[cell] = FaultType::NONE;   // <-- back to the original bug
}
```

This pattern repeats roughly every 2-3 iterations for the entire run: fix,
regress, fix, regress. Root cause, found by reading `smelt/core/phase2.py`:

**The Phase 2 reprompt never includes the current implementation source.**
`_build_prompt` (phase2.py:386) sends the spec, goals, test signatures, and
*only the most recent iteration's* compliance/goal failure detail — never
the code itself. The LLM call's system prompt says "Return ONLY the
corrected file," meaning every iteration **regenerates the entire
implementation from scratch**, informed only by the last failure list. If
`fault-cleared-outside-reset` isn't in that specific iteration's failure
list (because the previous iteration happened to fix it, or because a
clang-tidy nit crowded it out), the model has no persistent memory that the
else-clear was ever a problem, and the natural "recompute fault status from
the current reading" implementation — the exact failure mode
`demo_objectives.md` predicted from the start — reappears.

This matches CLAUDE.md's documented Phase 2 contract exactly ("Current
iteration number and score history" — not current code), so it is not a bug
relative to the written design. But this run is the first empirical evidence
of a real consequence of that design: **without code continuity, a fix that
isn't reinforced by that exact iteration's failure list can silently
un-fix itself**, indefinitely, regardless of how accurate the scorer is.
Fixing this would mean changing what the reprompt includes — a core-loop
architecture decision beyond the scope of today's specialist/composite work,
flagged here for a decision rather than made unilaterally.

## Assessment for the post

This is not the clean "iteration 1 fires, iteration 6 converges" arc
`demo_objectives.md` originally sketched, and after three runs it's now
clear that arc was optimistic about how reliably a single LLM call
regenerating a whole file from failure detail alone converges — independent
of whether the compliance scorer is correct. The more accurate and, taken
seriously, more interesting story: **the architecture-aware verifier caught
a real defect on 7 of 15 independent generation attempts, with perfect
precision and recall, while a stateless regenerate-from-scratch loop
repeatedly reintroduced the exact bug it had already fixed.** That is a
finding about LLM code generation loops in general — the verifier did
its job every single time; the generation strategy is the open problem.
