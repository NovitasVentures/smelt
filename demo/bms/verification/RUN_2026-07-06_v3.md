## The full arc that got here today

1. Three prior runs (`20260705_205805`, `20260705_215725`, `20260706_004627`)
   all hit the 15-iteration cap UNCONVERGED. The third proved the compliance
   scorer was fully accurate by hand (0 false positives, 0 false negatives
   across 15 iterations) — non-convergence was a **generator oscillation**:
   the reprompt only carried the most recent iteration's failure list, never
   the code itself, so a fix could silently un-fix itself on a later
   iteration with nothing in the prompt to stop it.
2. Added whole-file code continuity (previous implementation echoed back
   verbatim, framed as "edit this") and mandatory-principle reminders (every
   mandatory principle not currently failing gets a one-line "still
   enforced, do not reintroduce" note) — commit `cfa3725`.
3. First run with that fix (`20260706_021845`) reported **CONVERGED in 3
   iterations** — a dramatic improvement in iteration count. But hand
   inspection of the "converged" code found iteration 3's `update_cell` had
   a textbook else-clears violation via `faults_.at(cell) = FaultType::NONE`
   in a final else-branch — a real, undetected mandatory violation. The
   composite's `cleared_value_patterns` check only recognized `[]`-indexed
   and bare member assignment; `.at()`-indexed assignment (equally
   idiomatic, used constantly by this generator) fell through the regex
   entirely and was never flagged.
4. Fixed the regex (commit `11bfc0a`), added a permanent regression case
   (`pos__shape12_at_indexed_else_clear.cpp`) and four new unit test cases.
   Full 29-case suite still passes, PASS overall.
5. Re-ran (this run, `20260706_022743`) and hand-verified every iteration.

Given step 3 above, the loop's own CONVERGED report is not sufficient
evidence on its own anymore — it already produced one false positive today.
Every iteration's `monitoring/fault_manager.cpp` and
`supervision/battery_supervisor.cpp` was read directly:

|---|---|---|---|
| 1 | Laundered clear (`FaultType fault = FaultType::NONE; ... faults_[cell] = fault;`) | Fired | Correct — caught by the model fallback via `_cleared_value_assignment_verdict`'s laundering detection |
| 2 | Clean (no else-branch, no laundering) | Did not fire | Correct |
| 3 | `.at()`-indexed else-clear (`faults_.at(cell) = FaultType::NONE;` in final else) | Fired | Correct — this is the shape the `.at()` fix now catches |
| 4 (final) | Clean (no else-branch, no laundering, no `.at()` clear) | Did not fire | Correct |

Full-file grep of iteration 4's generated code for every occurrence of

`reset_faults()`/constructor, a `return` statement, or a `!=` comparison —
never an assignment outside a reset-named function. `battery_supervisor.cpp`
includes only `monitoring/` headers (no `hal/` leakage) across all 4
iterations, matching `LayerScorer`'s clean 1.00 the whole run.

The only compliance failure at convergence is `output-param-written-before-
error-check` (3 violations, non-mandatory, previously demoted for known

## Assessment

This is the outcome `demo_objectives.md` originally sketched — tests green
from iteration 1, compliance climbing, mandatory violations clearing — but
it took a materially different path to get there than assumed: not because
the generator naturally converges given enough attempts, but because the
reprompt needed code continuity to stop erasing its own progress, and the
composite scorer needed two more real-world hardening passes (the
local-variable-laundering fix and the `.at()`-indexing fix) before its
CONVERGED verdict could be trusted at all. Three real, previously-unknown
gaps in the deterministic composite tiers were found exclusively by running
the actual loop against genuinely novel LLM-generated code — none of them
were caught by the 25-29 case hand-authored verification suite, because
that suite's author (also the one writing the composite logic) had the same
blind spots the code was checking for.

**For the post**: this is worth being explicit about rather than polishing
away. The full session arc — from a 21/28 composite through demotions,
deterministic decomposition, two production-only false-negative escapes,
and a reprompt architecture fix — is the actual demonstration of what
"iteratively harden a verifier against a code generator" looks like in
practice. It is not a clean one-shot story, and that is more informative
than if it had been.
