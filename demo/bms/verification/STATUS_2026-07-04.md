## 1. Smelt core bugfixes (committed earlier this session, commit `ecb6266`)

- **`smelt/runners/gtest_runner.py`**: build-failure stderr was truncated to the
  last 500 characters, which discarded real compiler errors buried earlier in
  multi-file CMake output — the loop was reprompting on `[[nodiscard]]` warning
  noise instead of the actual error. Fixed with `_extract_failure_message()`,
  which greps for `error:` lines and keeps surrounding context, and removed
  `--parallel` from the build invocation so output ordering stays deterministic.
- **`smelt/core/phase1.py` + new `smelt/core/arithmetic_check.py`**: Phase 1's
  LLM computed integer-arithmetic conversions by hand when writing frozen tests
  (e.g. `(raw_counts * 5000) / 4095`) and got them wrong by 1, three times across
  independent runs — with zero validation catching it before freezing. Since
  tests are frozen and never touched again, this made affected runs unwinnable.
  Fixed with a formula-extraction + AST-based recompute + 3-attempt regenerate
  loop, mirroring the existing mutation-gate retry pattern in `_run_python`.

Both are tested (11 new unit tests) and verified against a real run (a live
mismatch was caught and correctly regenerated).

## 2. `fault-cleared-outside-reset` — single-specialist diagnosis (5 rounds)

The BMS demo has 5 Crasis specialists. Four converged cleanly. This one did not,
across rounds spanning:

1. **BERT-Tiny, range-based-for-loop gap.** `reset_faults`/`clear_faults` using a
   range-based loop over `std::array` scored as a false positive because training
   data only showed indexed loops. Fixed with new eval_on examples — but this
   surfaced further failures once fixed for these two cases.
2. **BERT-Mini capacity increase.** Raised `max_model_size_mb` from 20 to 43 to
   cross the threshold from BERT-Tiny (4.4M params) to BERT-Mini (11M params),
   theorizing the rule bundled too many distinct reasoning types (branch-flow,
   delegation, name-conditioning) for a 2-layer model. **Result: worse, not
   better** — 24/28, with a new regression and 3 violation cases scoring 98%+
   confident in the *wrong* direction (not just uncertain).
3. **Label-contradiction fix.** Direct inspection of `train.jsonl` found the
   real cause: of 113 range-based-loop training examples, 99 were negative and
   *zero* were the counter-example (range-loop clearing outside a reset-named
   function) — and `clear_all_faults()` was labeled negative 10/10 times as its
   own definition but positive ~80% of the time when called from elsewhere, a
   direct contradiction traced to the spec's fuzzy phrase "or a similar
   reset-named operation." Tightened trigger/ignore wording to require the
   *exact* name `reset_faults`/`clear_faults`, regenerated data from scratch.
   **Result: fixed all label contradictions (24/24 clean cases + the regression),
   but the same 3 violation shapes still failed at ~98.8% confidence, wrong
   direction, unchanged from before.**
4. **Vocabulary-rebalance fix.** Found that of 78 training examples using the
   *exact* project vocabulary (`FaultManager::`, `faults_[cell]`,
   `OVER_VOLTAGE_MV`), 71 were negative and 7 positive — a vocabulary-level
   shortcut, not just a range-loop one. Added 5 exact-vocabulary positive
   violation examples. **Result: statistically identical to before** — same 3
   cases, same ~98.8% wrong-direction confidence.
5. **Function-name-level diagnosis.** Deeper check found the shortcut operates
   at the literal function-name level: `update_cell` co-occurs with negative
   labels 170/217 times (78%) across the *entire* 4500-example set, `poll_cell`
   84/116 times (72%), and `sync_faults` had **zero** training examples of any
   label. Five added examples cannot meaningfully shift a ratio baked into
   hundreds of examples generated from spec text that inherently reuses the
   project's own vocabulary far more in "clean" (spec-quoted) examples than in
   "violation" (invented) ones.

**Conclusion at this point:** three consecutive rounds of increasingly targeted
data-quality fixes converged on the exact same wall. This ruled out capacity and
label-quality as the root cause and identified it as a genuine architectural
mismatch — a single small classifier cannot learn a name-conditioned exemption
and an identifier-blind data-flow judgment simultaneously when trained on
naturally-generated synthetic data, because the data itself cannot help but
correlate specific identifiers with specific outcomes.

## 3. Composite-specialist architecture (this session's main code change)

### Design

Split the one specialist into two, each with a narrow, structurally enforced
scope, combined by new logic in the scorer rather than by a single model:

- **`reset-name-exemption`** (specialist A): pure name/call-graph check —
  "is this function named exactly `reset_faults`/`clear_faults`, or does it
  purely delegate to one?" Trained on raw text. BERT-Tiny (4.3MB).
- **`fault-clearing-dataflow`** (specialist B): pure data-flow check — "does
  this function clear fault state via any control-flow path?" Trained on
  **identifier-redacted** text (class/function/member names replaced with
  generic placeholders `CLASS_0`/`FUNC_0`/`MEMBER_0`) so it is structurally
  incapable of learning an identifier shortcut. BERT-Mini (10.8MB).
- **Composite rule**: a chunk is a violation iff B fires positive AND A does
  NOT fire positive on the same (unredacted) chunk.

### Code changes

- **`smelt/scorers/chunker.py`**: new `redact_identifiers()` function.
  Deterministic per-chunk replacement (same identifier → same placeholder
  within one call), preserves C++ keywords/builtin types and enum-qualified
  values (`FaultType::NONE` stays intact). 7 new unit tests, all passing.
  - **Bug found and fixed during this work**: the member-redaction regex
    `\b[a-z_][a-zA-Z0-9]*_\b` could never match multi-underscore identifiers
    like `fault_manager_`/`monitor_` because the middle character class
    excluded `_`. This silently left real member names in specialist B's first
    round of "redacted" training data. Fixed to
    `\b[a-zA-Z_][a-zA-Z0-9_]*_\b`; specialist B was retrained after the fix.
- **`smelt/scorers/crasis_scorer.py`**: new composite-principle support. A
  `composites` config dict maps a principle name to
  `{violation_specialist, exemption_specialist, redact_for_violation}`.
  Composite constituents are excluded from independent per-specialist scoring;
  the composite name is scored via `_score_composite()`, which evaluates both
  specialists per-chunk and combines them with AND-NOT logic. `_aggregate()`
  and weight handling work unchanged since composites report violations under
  their own principle name, same as any other specialist.
- **`smelt/config/profiles/demo8_bms.toml`**: added
  `[scorers.crasis.composites.fault-cleared-outside-reset]` wiring
  `violation_specialist = "fault-clearing-dataflow"`,
  `exemption_specialist = "reset-name-exemption"`, `redact_for_violation = true`.
- **`demo/bms/verification/verify.py`**: `verify.py` previously only knew how
  to verify single specialists directly via `crasis.Specialist.load`. Added a
  `COMPOSITES` dict (kept in sync with the TOML) and `verify_composite()`,
  which classifies each case with both underlying specialists and applies the
  same AND-NOT logic `CrasisScorer` uses, so the verification harness and the
  real scoring path can't drift apart.
- **New specs** (gitignored, not committed): `demo/bms/specs/reset-name-exemption.yaml`,
  `demo/bms/specs/fault-clearing-dataflow.yaml`.
- **New trained specialists** (gitignored, not committed):
  `demo/bms/specialists/reset-name-exemption-onnx/`,
  `demo/bms/specialists/fault-clearing-dataflow-onnx/`.

### Results

**Direct 9-case validation (hand-picked, the known hard cases): 9/9 pass**,
including all 3 cases that failed across every round of the single-specialist
approach (else-clears, read-clears, range-loop-outside-reset), plus the
reinit-before-evaluate delegation case. This validated the core hypothesis:
splitting the exemption check from the data-flow check, with the data-flow
specialist trained on identifier-redacted text, structurally prevents the
identifier-shortcut failure mode that blocked 3 rounds of single-specialist
retraining.

**Full 28-case suite (`verify.py --only fault-cleared-outside-reset`): 21/28.**
The broader suite — which the 9-case spot check did not cover — surfaced a
different problem: specialist B produces false positives on read-only and
pass-through functions it had never seen a negative example of:

- `neg__has_any_fault` (pure read loop, comparison only, no assignment)
- `neg__read_cell_temp` / `neg__read_cell_voltage` (pass-through conversion
  functions with zero member references at all)
- `neg__shape3_query_local_init` (local-variable-only, no member assignment)

Three additional apparent failures (`neg__*_ctor` cases) are **not a real
production risk** — confirmed via direct `chunk_code()` testing that
`smelt/scorers/chunker.py`'s constructor-skip regex filters constructors out of
scoring whenever a real function coexists in the same file (which it always
does in generated code). `verify.py` classifies isolated case-file snippets
directly, bypassing the chunker, so these 3 cases test an input shape the real
pipeline never produces. They should be considered a harness artifact, not a
specialist defect — but they still show up in the raw pass count.

**Round 2 attempt**: added 6 new negative eval_on examples targeting the 4 real
false positives (pass-through chains, read-only loops), regenerated all 4493
training examples from scratch, retrained. Result: `has_any_fault` fixed, but
`read_cell_temp`/`read_cell_voltage`/`shape3` still failed, and `shape7`
(reinit-before-evaluate, which had passed in round 1) regressed back to
failing. **Net effect: still ~21/28, different mix of failures** — the same
oscillating "fix one shape, another shifts" pattern seen in the original
single-specialist saga, now relocated into specialist B.

No third retrain round was attempted. Per established practice this session
(check in before further retrain cycles once a pattern of diminishing/oscillating
returns appears), I stopped and asked how to proceed; the user has now asked for
this report instead, to reflect on next steps before any further specialist work.

## Open questions / decisions needed

1. **Is 21/28 acceptable, or does specialist B need a third round?** Two rounds
   of targeted negative examples have not converged; a third round would need
   either much heavier negative weighting (15-20+ examples instead of 6) or a
   different strategy (e.g., a stricter trigger condition requiring an explicit
   assignment token count above zero, checked programmatically rather than
   learned). Given the oscillating pattern, there's a real risk a third round
   just shifts the failure mix again without net improvement.
2. **Has the smelt loop actually reached CONVERGED this session?** No — this
   has not yet been tested with the composite specialist in its current state,
   because `fault-cleared-outside-reset` is a `mandatory_principles` entry and
   the composite currently fails 7/28 cases. A full `smelt run` has not been
   launched since wiring in the composite. This is the natural next step once
   a decision is made on (1).
3. **Is the composite architecture worth keeping regardless of this specific
   rule's outcome?** The `redact_identifiers()` + composite-scorer
   infrastructure in `crasis_scorer.py` is generic — it isn't specific to
   `fault-cleared-outside-reset` and could apply to any future rule with the
   same "small model learns identifier shortcuts" failure mode. This is
   reusable infrastructure independent of whether this particular rule ever
   reaches a clean pass.
4. **Blog-post material.** The user has flagged this whole arc — BERT-Tiny→Mini
   capacity red herring, then label contradictions, then vocabulary shortcuts,
   then function-name shortcuts, then the composite architecture's own
   depth-vs-breadth tradeoff — as valuable narrative content for a planned post
   on specialist size/performance/data tradeoffs. The diagnosis chain is
   unusually clean as a teaching example: each fix was verified against the
   actual crasis training data before being applied, and each "fix" that didn't
   work was caught by direct measurement rather than assumption.
5. **`demo/bms/specialist_authoring.md`** has not been updated this session
   with the composite-architecture build history. If the user wants this
   documented (build history table, the 5-round single-specialist diagnosis,
   the composite round 1/2 results), that's a separate pending task.
