**Result: UNCONVERGED after 15 iterations (cap).** Final composite 0.00 (a

## The money moment showed up as designed

For **12 consecutive iterations (2 through 12 plus 1)**, all 60 frozen GTest
tests passed (`goal_score = 1.00`) while compliance sat at 0.80-0.81 —
below the 0.90 threshold — because `LayerScorer` stayed clean (1.00 throughout;
the generator never leaked `hal/` into `supervision/`) but Crasis held at 0.60,
driven by the same two mandatory architectural violations every iteration:

- `fault-cleared-outside-reset [mandatory]` firing on `FaultManager::update_cell`
  and `BatterySupervisor::poll_cell`
- `output-param-written-before-error-check` firing on `CellMonitor::to_millivolts`,
  `CellMonitor::to_deci_celsius`, `BatterySupervisor::get_last_voltage`

This is exactly `demo_objectives.md`'s "every test passed, the system still
refused to ship it" framing, live: a behaviorally-complete implementation held
below the compliance bar by principles no test in the suite can see.

## The catch: both persistent ARCH firings are the two known false positives, not real violations

Direct inspection of the generated code shows **neither firing is a genuine
architectural violation**:

- `fault_manager.cpp`'s `update_cell` never writes `FaultType::NONE` — it only
  ever sets fault values across three `if`/`else if` branches with no final
  `else`. This is the textbook non-self-clearing implementation the demo wants,
  and it is the exact `neg__poll_cell` false-positive shape documented in
  `specialist_authoring.md` build 8 (two read-delegate calls, then member-array
  writes, no clearing call, no reset call) reproducing on real generated code —
  the accepted, root-caused gap from this session's retrain track, now
  confirmed to actually occur rather than being a synthetic worry.
- `output-param-written-before-error-check`'s three firings are on
  `to_millivolts`/`to_deci_celsius`/`get_last_voltage` — the same 3-of-5 core
  spec-API conversion/read functions this specialist has false-positived on
  since the build-2 retrain (`report.md`, 23/28). This is exactly why it was
  demoted from `mandatory_principles` this session — it never blocked
  convergence in this run (only `fault-cleared-outside-reset` is mandatory
  among the two), but its noise is present in every iteration's reprompt,
  which likely absorbed some fraction of the model's attention without ever
  being fixable (there's nothing wrong with the code to fix).

**The layer violation and the else-clear that `demo_objectives.md` predicted
as "expected with high confidence" did not occur.** The generator produced a
clean 3-layer implementation with no else-clear from iteration 1 onward. Per
the honest-reporting commitment (Demo 4a precedent): this is a negative
result for those two specific predictions, reported as observed, not as
expected.

One new false positive was found that the 25/28-case verification suite does
not cover: iteration 14's `raw-threshold-comparison-in-decision-logic` fired
on `CellSensor::configure` (a test-injection setter that stores raw values
behind a bounds check — no threshold comparison, no decision logic). Not
persistent (only iteration 14), but a real gap in verification coverage,
not a synthetic worry.

## The build-failure regression that ended the run

Iterations 13 and 15 both failed to build (`goal_score = 0.00`, composite
crashes to 0.00 regardless of compliance). Root cause, confirmed by diff:
the generator introduced a `CellConfig` aggregate struct for
`CellSensor::configure` to silence clang-tidy's
`bugprone-easily-swappable-parameters` (flagged every iteration on
`configure`'s 3 same-typed `int32_t`/`bool` parameters), changing the
signature from `configure(uint8_t, int32_t, int32_t, bool)` to
`configure(uint8_t, CellConfig const&)`. The frozen tests call the 4-argument
form (`sensor.configure(3, 2867, 0, true)`), so this change cannot compile
against them. Iteration 14 reverted to the compatible signature and passed
all tests again — but iteration 15, the last one under the 15-iteration cap,
regressed right back to the incompatible `CellConfig` struct, ending the run
on a build failure rather than a scored compliance gap.

This is a real correctness defect in the generator's behavior under the
"do not modify test files — fix the failures described, do not introduce new
ones" instruction: it repeatedly traded a passing, frozen-test-compatible
build for a stylistic clang-tidy fix, twice, with no memory that the trade
had already failed once. Nothing in Smelt's core loop is implicated — the
loop correctly caught the regression (`goal_score` cratered, the reprompt
carried the build error) — this is generator behavior under iteration
pressure with a plausible/swappable-parameters clang-tidy nit competing
against test compatibility for the model's attention on the final iterations.

## Overall assessment

- **The core Smelt claim held**: tests green, compliance blocked by real
  architectural gating (LayerScorer clean, Crasis mandatory principles
  enforced), never conflated. The composite/demotion decisions from this
  session mean the run was not vacuously blocked by known-bad specialists
  (`output-param` no longer mandatory) — but a different accepted false
  positive (`neg__poll_cell`'s real-world analog) was, for 12 iterations,
  the sole thing standing between 0.81 and the 0.90 threshold.
- **UNCONVERGED, not FAILED-to-demonstrate**: the run never got a clean shot
  at closing the compliance gap because it was structurally pinned at 0.60
  Crasis score for 12 iterations by a false positive with no counterexample
  the generator could produce (the flagged functions are already correct;
  there is no code change that resolves an incorrect classification). The
  build-failure oscillation on iterations 13/15 then burned the remaining
  budget instead of ever testing whether resolving that pin would have
  converged.
- **Two concrete follow-ups surfaced, not yet actioned**: (1) the
  `neg__poll_cell` gap from the retrain session is now confirmed to occur on
  real generated code, raising its priority above "theoretical, hasn't been
  observed"; (2) a new `raw-threshold-comparison-in-decision-logic` false
  positive on setter/injection functions, previously unseen, needs a case
  file and either a trigger-gate fix or an eval_on addition.
- **For the post**: this run is not the clean "iteration 1 fires, iteration 6
  converges" arc `demo_objectives.md` sketched. It's a more honest and
  arguably more interesting one — the loop correctly refused to converge on
  a plausible-looking implementation for 12 iterations, and the reason
  turned out to be a real, traceable specialist defect rather than a real
  architectural violation. Reporting that distinction accurately is more
  valuable than re-running until it happens to converge.
